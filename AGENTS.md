# AGENTS.md — QSKOS

QGIS plugin for semantic annotation of vector features with SKOS vocabularies, stored in a GeoPackage, with rule-based
symbology and a Linked Open Data export (DCAT, GeoSPARQL, Web Annotation, CIDOC CRM crosswalk).
Layout: `qskos/` (the plugin package; `qskos/libs/` = bundled rdflib, never edit), `tests/`, `tools/` + `ontology/` + `docs/`
(export model, generated GitHub Pages docs), `context/` (workflow docs for agents and humans), `scripts/` (QGIS install, test runner).

## Read first — and only this
1. Your work package `context/work-packages/WP-xxx.md`. Do only that package.
2. The files and **sections** it lists under "Read first". Do not read whole documents when a section is named.
3. `context/adr/README.md` (one line per decision). Open a full ADR only if the package lists it or the index line is not enough.
4. `context/STATUS.md` (one page, what exists today).

Do not read `CHANGELOG.md` (only prepend your entry), `context/reference/` (background specs, partly outdated; code and ADRs win)
or `qskos/libs/`. `docs/*.md` and `ontology/example.ttl` are generated by `python tools/main.py`; never edit them by hand.
Accepted ADRs are not re-opened; if one blocks you, stop and say so.

## Batch cycle
Work runs in batches the human starts. One batch = a handful of packages that fit together.
1. **Prepare** (human asks for the next batch): pick the next packages from `context/roadmap.md`, write or update their files (draft), and give
   the human **one list** of every decision and input they need, each with a recommendation. Do not implement yet.
2. **Approve:** write the human's answers into the packages, `context/open-questions.md` (and ADRs if a decision is architectural). Set
   `Status: ready` only when the human told you to or agreed when you asked explicitly. Never set `ready` on your own judgment.
3. **Implement:** run `make next`; work only on packages under "Delegable now" (`Status: ready`, all dependencies `review` or `done`), one
   after another in dependency order, one commit series each. Never start a roadmap row without a file or with `Status: draft`.
   Per package: `make test` and `make test-qgis` pass → `Status: review` if the tier contains `review`, otherwise `done`; update
   `context/STATUS.md`; prepend a `CHANGELOG.md` entry; continue with the next ready package. Report when the batch is finished or you are blocked.
4. **Review:** the `review`-tier packages of the batch are reviewed together (`context/review-checklist.md`) in a fresh session.
If nothing is delegable, **stop** and say which packages need to be written or approved (that is step 1).

## Commands
- `make test` — unit + export tests, no QGIS (`uv run pytest`). `make test-qgis` — QGIS-bound and end-to-end tests in real, headless QGIS
  (`scripts/run_qgis_tests.sh`; set up once with `sudo scripts/install_qgis_ubuntu.sh`). `make docs` — rebuild ontology example and `docs/`.
  `make next` — work package status. CI runs both test suites on every push and pull request.
- Python is managed with `uv`; never use `pip install`. The plugin itself has no runtime dependencies beyond QGIS and `qskos/libs/`.

## Engineering rules
- **Read before write.** Search `qskos/` for an existing helper before creating one.
- **Extend, don't copy.** Never create `foo_v2`; refactor the original (parameters, composition).
- **Size limits (soft):** ~300 lines per file, ~50 lines per function. Before adding to a file above the limit, split it in a separate commit.
  Exempt: `qskos/libs/`, test files (≤ 600), generated files.
- **State in classes, logic in pure functions.** Shared state, GeoPackage access and services live in classes; stateless transformations
  (parsing, hierarchy, rule planning, RDF building) are pure functions without Qt/QGIS imports and have unit tests.
- **Tabs stay thin.** `qskos/tabs/` build widgets and translate UI events into service calls; no SQL, no RDF, no rule logic in tabs.
- **No dead code.** Delete instead of commenting out.
- **Stay in scope.** Clean up only code you are changing anyway. Anything else → note it in the summary.
- **Tests are part of the change.** Pure modules: `pytest` in `tests/test_*.py`. Anything touching QGIS objects, widgets or signals:
  `pytest-qgis` in `tests/test_qgis_*.py`.
- **No new dependency** without naming it and the reason in the summary (a new bundled lib goes into `qskos/libs/`).
- Specs, code, commits and comments are English. User-facing strings in English (no i18n yet, see `context/open-questions.md`).

## QGIS rules (each one was a real bug)
- **Verify in real QGIS through the real path.** Drive widgets and signals (combo → list → tree checkbox, editor widget wrappers) instead of
  setting state or writing values directly. A test that bypasses the widget proves nothing about what the widget stores.
- **Check every result.** `commitChanges()`, `startEditing()`, `addAttribute()` return booleans; on failure report `commitErrors()`.
- **Respect the user's edit session.** Never commit or roll back a layer the user is editing.
- **Fields must match the provider's native type** exactly (type, typeName, subType), or the commit is rejected (ADR-0001).
- **Block signals** around programmatic `setCheckState`/list rebuilds, and expect widgets (e.g. `QgsMapLayerComboBox`) to re-emit for the same value.
- **GeoPackage writes go through `qskos/utils/gpkg.py`**; never drop or alter a table that is not a qskos table (ADR-0002).
- **No network in parsers** except the explicit "Remote URL" import, which must time out and run off the GUI thread (WP-006).
- "Resolved" needs a regression test that fails on the old code. Do not mark items resolved in docs on reasoning alone.

## Security-sensitive areas (tier `review`; run `context/review-checklist.md`)
RDF/CSV parsers and remote vocabulary loading, any SQL against the GeoPackage, schema changes of user tables, the export (output must be
valid RDF for any user input).

## Workflow
- Trunk-based: commit and push directly to `master` (the second collaborator pushes only rarely). Use a branch + pull request only when
  the human asks for one. One work package = one commit series. Pull before you push.
- If the spec is ambiguous or contradicts the code, do not guess: add the point to `context/open-questions.md`. If it blocks the package, stop
  and ask; otherwise continue with the rest of the batch and list the question in the report.
- If the tests still fail after two fix rounds, stop and report instead of trying further.
